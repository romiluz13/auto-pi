# auto-pi v0.5 — autonomous multi-agent workflows via intercom

**Status:** Proposed (PLAN phase)
**Date:** 2026-08-16
**Supersedes:** v0.4 (ask-matt router + orchestration layer) — extends it with multi-agent autonomy
**Evidence:** Temporal x MongoDB session logs (`~/.pi/agent/sessions/--Users-rom-iluz-Dev-Temporal x MongoDB--`), pi-intercom README, auto-pi config/agents.md, orchestration-layer skill

---

## The goal

**One command. Full autonomy.** The human types `/orchestrate <goal>` once. The system plans, dispatches workers, they build + ask each other questions, the manager answers + merges + ships — with **no other human input**, ever, except for genuine money/legal/public-compatibility decisions. The system self-heals (intercom broker dies → restarts; worker crashes → relaunches; merge conflict → resolves by intent). It runs a bounded loop until the goal is shipped. It detects stuck/dead workers + recovers. It is fully autonomous for every technical + product decision.

Two (or more) agents talk via intercom. Each runs auto-pi workflows (/plan, /build, /review, /ship). They coordinate autonomously — ask each other questions, resolve everything. The manager plans + dispatches; the worker builds + asks; both ship without human-in-the-loop. Workers can spawn their own sub-workers (recursive delegation). The manager monitors progress, detects failures, recovers, merges, ships.

## The current state — what works, what's broken

### What works ✅

- **Intercom 1:1 messaging** — `send` (fire-and-forget), `ask` (blocks for reply, 10-min timeout), `reply`, `pending`. Auto-trigger on inbound (`inboundTrigger: "always"`). Reply hints included. We dogfooded ping/pong + the manager/slave roleplay successfully.
- **Single-agent workflows** — one Pi session runs /plan → /build → /review → /ship via Coach → ask-matt → orchestration-layer → workflow interpreter. 95/95 tests pass. v0.4 shipped.
- **Read-only subagent fan-out** — research/review subagents (fresh context, read-only) work for parallel research + review.

### What's broken ❌ (the "naked agent" problem)

Evidence: Temporal x MongoDB session logs (2026-08-16). GLM 5.2 was told to "delegate aggressively" to a worker agent. Every delegation path failed:

| # | What GLM 5.2 tried | Why it failed |
| --- | ------------------- | --------------- |
| 1 | Launch `researcher` subagent | **Blocked** — workflow ceiling allows only `reviewer` agents as children |
| 2 | Launch `reviewer` with a research task | **"Workflow quarantine: Active workflow already owns this repository"** — child can't operate in the repo cwd |
| 3 | Retry with cwd outside repo + output to /tmp | **Output path collided** with the workflow aggregate output |
| 4 | Disable file output, return inline | Child launched but **had no web tools** — only `read`, `grep`, `find`, `ls`, `contact_supervisor` |
| 5 | `subagent status` to check the child | **Blocked** by the workflow capability ceiling |

The subagent transcript confirms: *"I do not have the web research tools (`web_search`, `fetch_content`, `source_check`) available in my toolset. My only available tools are `read`, `grep`, `find`, `ls`, and `contact_supervisor`."*

GLM 5.2 fell back to doing all research itself. **No delegation happened. No artifact was produced. The project dir is empty.**

### The 5 root-cause gaps

1. **Subagents run "naked."** A subagent launched via the `subagent` tool gets basic tools (read/grep/find/ls) but NOT Coach, orchestration-layer, ask-matt, the workflow interpreter, or web tools. It can't run workflows. It can't research. It's a raw agent.

2. **Workflow repo quarantine.** The workflow interpreter "owns" the repo. When agent A has an active workflow, agent B (subagent or separate session) can't work in the same repo cwd. Two agents can't both run workflows in the same repo.

3. **USER_DECISION_REQUIRED is human-in-the-loop.** When a workflow hits a hard decision, it stops for a human. The user wants agents to ask EACH OTHER via intercom instead. There's no mechanism to route a workflow decision to another agent.

4. **No inter-agent workflow invocation.** Agent A can send an intercom message to agent B, but agent B can't start a workflow from that message. Coach intercepts HUMAN input (the `input` event), not intercom messages. An agent can't programmatically tell another agent "run /build for ticket X."

5. **Coach is human-driven.** Coach shows a 9-option menu to a HUMAN (with a 20s auto-pick timer). An agent can't pick from Coach's menu. So a worker agent can't use Coach to start a workflow autonomously.

## The target architecture

```
Manager agent (Pi session, full auto-pi)
  │
  ├── /plan → spec + tickets (workflow interpreter, human OR agent decides)
  │
  ├── intercom send to Worker: "run /build for ticket #X in worktree X"
  │                                      │
  │                                      ▼
  │                              Worker agent (Pi session OR subagent, full auto-pi)
  │                                      │
  │                                      ├── /build #X (workflow interpreter, TDD, evidence gates)
  │                                      │      │
  │                                      │      ├── hits ambiguity → intercom ask Manager → Manager replies → continues
  │                                      │      ├── hits hard decision → intercom ask Manager (NOT human) → continues
  │                                      │      └── /build complete → intercom send Manager: "ticket #X done"
  │                                      │
  │                                      ├── /review → code-review + security (fresh subagents)
  │                                      └── /ship → verify + commit (in its worktree)
  │
  ├── Manager picks next ticket → intercom send Worker: "run /build for #Y"
  └── all tickets done → Manager runs /ship (merge worktrees, final commit, PR)
```

### The 3 changes that enable this

#### Change 1: Auto-pi for subagents (the "workflow-worker" agent type)

**Problem:** Subagents run naked — no Coach, no workflow interpreter, no web tools.

**Fix:** A new agent type `workflow-worker` (or a launch flag) that loads the full auto-pi stack: the workflow interpreter (workflow_exec, workflow_transition), orchestration-layer, ask-matt, and the standard toolset (web_search, fetch_content, bash via workflow_exec). When the manager launches a `workflow-worker` subagent, the child can run /build, /review, /ship autonomously.

**Worktree isolation:** Each `workflow-worker` gets its own git worktree (`worktree: true`) so the repo quarantine doesn't conflict. The manager owns the main worktree; workers own branch worktrees. No two agents write to the same files.

#### Change 2: Inter-agent workflow dispatch (intercom → workflow start)

**Problem:** Agent A can't tell agent B "run /build for ticket X." Coach only intercepts human input.

**Fix:** A new extension (or a Coach mode) that listens for intercom messages of shape `{ action: "workflow-request", command: "/build", arg: "#X" }` and starts the workflow — the same path as a human typing `/build #X`. This is "Coach for agents": the manager agent plays the role of the human, sending intercom messages that Coach (or a new `agent-coach` extension) intercepts + routes into the workflow interpreter.

**Two modes:**

- **Subagent mode:** the manager launches a `workflow-worker` subagent with a task like "run /build for ticket #X." The subagent's entry prompt is the workflow pin (orchestration-layer). No intercom needed for dispatch — the launch IS the dispatch. Intercom is only for questions during the work.
- **Separate-session mode:** the manager sends an intercom `send` to a separate Pi session with a `workflow-request` payload. The recipient's `agent-coach` extension intercepts it + starts the workflow.

#### Change 3: Autonomous decision resolution (USER_DECISION_REQUIRED → intercom ask)

**Problem:** Hard decisions stop for a human. The user wants agents to ask each other.

**Fix:** A new workflow event `AGENT_DECISION_REQUIRED` (or extend USER_DECISION_REQUIRED with a `delegateTo` field). When the workflow hits a hard decision, instead of stopping for a human, it sends an intercom `ask` to the designated agent (the manager). The manager replies. The workflow resumes with the answer — the same path as USER_DECISION_RESOLVED, but the answer came from another agent, not a human.

**Guardrail:** The decision class still matters (public-compatibility, production-data, money, legal-security, release-authority). For genuinely human-owned decisions (money, legal), the manager can still escalate to the human. For technical decisions, the manager agent resolves them.

## What collapses, stays, is new

### Stays (v0.4 architecture)

- Coach (for human-driven sessions — unchanged)
- ask-matt (routing brain — unchanged)
- orchestration-layer (mechanics — unchanged)
- workflow-machine + workflow-interpreter (control plane — unchanged, extended)
- The 14 repo skills (unchanged)
- Intercom (unchanged — the transport)
- The evidence gates (unchanged — workers satisfy the same gates)

### Is new

| Component | What it is |
| ----------- | ----------- |
| `workflow-worker` agent type | A subagent that loads the full auto-pi stack (workflow interpreter, orchestration-layer, ask-matt, web tools) + gets its own worktree. The "non-naked" worker. |
| `agent-coach` extension (or Coach agent mode) | Listens for intercom `workflow-request` messages + starts workflows. "Coach for agents." Enables a manager agent to dispatch workflows to a worker session. |
| `AGENT_DECISION_REQUIRED` event | Routes hard decisions to another agent via intercom instead of stopping for a human. The manager resolves; the workflow resumes. |
| Worktree-per-worker protocol | The manager owns the main worktree; each worker gets a branch worktree. No repo quarantine conflict. The manager merges at ship. |
| `multi-agent-orchestration` skill | The procedure the manager agent follows: plan → dispatch tickets to workers → answer questions → merge → ship. |

### Collapses / changes

- The "subagents are read-only reviewers" ceiling — relaxed for `workflow-worker` agents (they can write, in their own worktree).
- The "one writer per repo" rule — becomes "one writer per worktree." Multiple workers can build in parallel in separate worktrees.

## Full autonomy: the 6 missing pieces

The 3 changes above enable multi-agent dispatch. **Full autonomy** requires 6 more pieces — without them, the system dispatches but can't recover, detect stuck workers, or run unattended.

### A1: The autonomous orchestration loop (the heart)

**Problem:** The current spec dispatches tickets once. It doesn't loop. It doesn't detect when a worker is done, stuck, or dead. It doesn't advance to the next ticket autonomously.

**Fix:** The `multi-agent-orchestration` skill defines a **bounded loop**, not a single dispatch:

```text
loop:
  1. Pick the next unblocked ticket from the frontier.
  2. Launch a workflow-worker subagent (worktree-isolated) for it.
  3. While the worker runs: answer its intercom asks (questions, decisions).
  4. Detect completion: worker sends "ticket #X done" via intercom.
  5. Merge the worker's worktree branch into the manager's worktree.
  6. If merge conflicts → resolve autonomously (A4).
  7. Advance: mark the ticket done, reduce the frontier.
  8. If frontier empty → break to ship. Else → loop.
ship:
  9. Run /review (fresh reviewers) + /ship (verify + commit + PR) on the merged result.
```

**Bounded:** the loop has a finite cap (e.g., max 20 tickets, max 3 retries per ticket). Every cycle changes the progress fingerprint (a ticket moves from open → done). No infinite loops.

**Self-advancing:** the manager never asks the human "should I do the next ticket?" It consumes the frontier autonomously until the map clears or a hard decision (money/legal) is reached.

### A2: Failure recovery + the escalation ladder

**Problem:** What happens when a worker crashes, sticks, or hits an unsolvable bug? The current spec doesn't say. The system would hang.

**Fix:** A bounded escalation ladder:

```text
worker fails (crash, timeout, no progress for N minutes):
  attempt 1: relaunch the worker (fresh context, same ticket)
  attempt 2: relaunch with a different model (if configured) or different approach
  attempt 3: the manager diagnoses the ticket itself (runs /debug on the failure)
  if still failing: AGENT_DECISION_REQUIRED to the manager → manager decides:
    - reassign to a different ticket decomposition
    - escalate to human (ONLY if money/legal/public-compatibility)
    - park the ticket + continue with the rest
```

**Stuck detection:** the manager polls each worker via intercom `status` (or a heartbeat). If a worker shows no progress for N minutes (configurable, default 10), it's marked stuck → escalation ladder.

**Bounded retries:** max 3 attempts per ticket. Each retry changes the progress fingerprint (different model, different approach, or diagnosis evidence). No infinite retries.

### A3: Self-healing intercom

**Problem:** We've seen the intercom broker go stale (the Jul 18 broker running old code), broken symlinks, wrong IDs. If intercom dies mid-orchestration, the workers can't ask questions + the manager can't dispatch.

**Fix:** The manager runs an intercom health check before each dispatch + each answer:

- `intercom status` — if disconnected, restart the broker (`kill` stale PIDs, let it auto-spawn).
- If a worker is unreachable (not in the session list), mark it dead → escalation ladder (A2).
- If the broker socket is stale, remove it + let the broker respawn.

This is the fix we already applied manually (kill stale broker → auto-restart). A3 automates it.

### A4: Autonomous merge + conflict resolution

**Problem:** Two workers build in separate worktrees. When the manager merges their branches, conflicts can occur. The current spec says "detect conflicts + route to remediation" — but that's vague. Full autonomy means the manager resolves conflicts without a human.

**Fix:** The manager uses the `resolving-merge-conflicts` skill (already installed) — resolve by **intent** traced to each side's primary source (the spec + the ticket), not by asking the human. If the conflict is genuinely ambiguous (two valid interpretations), the manager picks the one that best serves the spec + records the decision. Only if the conflict reveals a spec contradiction does it escalate (AGENT_DECISION_REQUIRED to the manager itself, or USER_DECISION_REQUIRED if it's a public-compatibility question).

### A5: The `/orchestrate` one-command entry

**Problem:** There's no single entry point. The human has to type /plan, then somehow trigger orchestration. That's not "one command."

**Fix:** A new `/orchestrate <goal>` prompt that:

1. Pins `multi-agent-orchestration` (the skill with the bounded loop).
2. Starts the workflow interpreter in PLAN phase (terminal=shipped).
3. The manager agent runs the full autonomous loop (A1) until ship.

The human types `/orchestrate build a Temporal + MongoDB demo app` once. The system runs until the PR is opened. No other human input.

**Coach integration:** `/orchestrate` is a 10th Coach option (or replaces /plan when the goal is multi-ticket). The 20s auto-pick timer still applies.

### A6: Recursive delegation

**Problem:** A worker building ticket #X might need to research an API (validate external tech). The current spec says workers run /build — but /build doesn't include research delegation. The worker would have to do research itself.

**Fix:** A `workflow-worker` can spawn its own read-only subagents (research, review) — recursive delegation. The worker is the "manager" of its own sub-tree. The same worktree-isolation + intercom-ask rules apply recursively.

**Constraint:** recursion depth is bounded (default 2: manager → worker → research-subagent). No infinite recursion.

### A7: Self-healing stale workflow locks (the manager's own deadlock)

**Problem — proven in production 2026-08-16:** A workflow run starts, claims `active.lock` on the repo, then the Pi session crashes/reloads. The lock file persists (it's on disk under `~/.pi/agent/workflows/<id>/active.lock/owner.json`). On next session start, the workflow interpreter sees the lock, treats it as authoritative, and **disables shell execution + blocks `rm`/`kill` even via `workflow_exec`**. The model is locked out of clearing the lock because the safety guard treats the lock as authoritative — even though the owning PID is dead.

This is a **deadlock**: the lock is stale, but the only tools that could clear it are the ones the lock disables. The user had to manually `rm -rf` the lock from a real terminal. This is the single worst autonomy failure — a dead lock blocks ALL real work, and the system can't self-heal.

**Fix:** The workflow interpreter must validate the lock is live before honoring it:

1. On session start, read `active.lock/owner.json` → get the `pid` + `processBootNonce`.
2. Check if the PID is alive (`process.kill(pid, 0)` — non-destructive, just tests liveness).
3. If the PID is dead (or the boot nonce doesn't match the current process), the lock is **stale** → the interpreter **reclaims it**: overwrites `owner.json` with the current session's ID + PID + boot nonce, OR removes the lock + starts fresh.
4. If the PID is alive but it's a different process (not this session), honor the lock (real conflict).

**Guardrail:** reclamation only happens when the owning PID is provably dead. A live PID that's just slow is NOT reclaimed (that would steal a real run's lock). The check is `process.kill(pid, 0)` — throws if dead, returns if alive.

**This is the highest-priority autonomy piece.** Without it, any Pi crash/reload deadlocks the repo until a human clears the lock manually. Full autonomy is impossible if the system deadlocks on its own stale state.

## Open design decisions

### D-1: Subagent mode vs separate-session mode — which is primary?

**Subagent mode:** the manager launches `workflow-worker` subagents. Pros: same process, worktree isolation built in, the launch IS the dispatch. Cons: subagents share the parent's process (if it crashes, all crash); limited to the subagent tool's capabilities.

**Separate-session mode:** the manager sends intercom to independent Pi sessions. Pros: full isolation, each session has its own Coach + workflow interpreter. Cons: harder to coordinate; need the `agent-coach` extension; need worktree coordination across sessions.

**Proposal:** **Subagent mode primary** (simpler, built-in worktree isolation), separate-session mode as a fallback for long-running or cross-project work. Confirm.

### D-2: How does the worker get auto-pi capabilities?

**Option A:** A new agent type `workflow-worker` registered in the subagent config, with the auto-pi extensions + workflow interpreter injected.

**Option B:** Launch a separate Pi process (`pi --model X --workflow`) as the worker, with full auto-pi.

**Proposal:** **Option A** (subagent type) for simplicity. The subagent's system prompt pins orchestration-layer + ask-matt (same as a human /build invocation). The workflow interpreter runs in the child. Confirm.

### D-3: Does the workflow interpreter support multi-agent (per-worktree ownership)?

**Problem:** The current workflow interpreter quarantines the repo. Two agents in the same repo conflict.

**Fix:** The interpreter keys workflow ownership on the worktree path, not the repo root. Agent A owns `repo/` (main worktree); agent B owns `repo-worktree-X/`. Each has its own workflow run, its own journal, its own evidence gates.

**Proposal:** Extend the workflow interpreter to key on worktree path. Confirm.

### D-4: AGENT_DECISION_REQUIRED — new event or extend USER_DECISION_REQUIRED?

**Option A:** New event `AGENT_DECISION_REQUIRED` with a `delegateTo` field (the target agent). The workflow sends an intercom `ask`, the reply becomes the resolution.

**Option B:** Extend `USER_DECISION_REQUIRED` with an optional `delegateToAgent` field. If set, the workflow asks the agent first; if the agent can't resolve, it escalates to the human.

**Proposal:** **Option A** (new event) for clarity — agent-resolved vs human-resolved are different flows. The manager agent resolves technical decisions; only genuine human-owned decisions (money, legal) hit USER_DECISION_REQUIRED. Confirm.

### D-5: What does the `multi-agent-orchestration` skill contain?

The procedure the manager agent follows — the **bounded autonomous loop** (A1), not a single dispatch:

1. Run /plan → spec + tickets
2. **Loop** (bounded, self-advancing):
   - Pick the next unblocked ticket from the frontier
   - Launch a `workflow-worker` subagent (worktree-isolated) for it
   - While the worker runs: answer its intercom asks (questions, decisions)
   - Detect completion (worker sends "ticket #X done") OR stuck (A2: no progress for N min → escalation ladder)
   - Merge the worker's worktree branch (A4: resolve conflicts autonomously by intent)
   - Mark the ticket done, reduce the frontier
   - If frontier empty → break to ship; else → loop
3. Ship: /review + /ship on the merged result
4. If a worker hits a hard decision: resolve it (AGENT_DECISION_REQUIRED) or escalate to human (ONLY money/legal)

**Proposal:** This skill is pinned by the new `/orchestrate` prompt (A5). It contains the loop, the escalation ladder, the self-healing intercom check, + the merge procedure. Confirm.

### D-6: How does the manager detect a stuck/dead worker?

**Problem:** The manager dispatches a worker + waits for its "done" intercom message. But if the worker crashes, hangs, or silently fails, the manager waits forever.

**Options:**

- **A:** Intercom heartbeat — the worker sends `intercom send` with a progress update every N minutes. The manager detects missing heartbeats.
- **B:** Intercom `status` polling — the manager polls `intercom list` for each worker's status (idle/thinking/tool). No progress (stays idle) for N min → stuck.
- **C:** Subagent `status` — the manager uses `subagent status` to check the child's state.

**Proposal:** **B** (intercom status polling) — it's the simplest, uses existing intercom, doesn't require worker cooperation. The manager polls every 2 min; idle for 10 min → stuck → escalation ladder (A2). Confirm.

### D-7: What's the recursion depth for recursive delegation (A6)?

**Problem:** A worker spawns a research subagent. That subagent could spawn its own. Infinite recursion is possible.

**Proposal:** Bounded at depth 2 (manager → worker → research/review subagent). The research/review subagents are read-only (no further spawning). Configurable via a setting. Confirm.

## Acceptance criteria

The refactor is complete when:

1. **One command starts everything** — the human types `/orchestrate <goal>` once. No other human input until the PR is opened (except money/legal).
2. **A `workflow-worker` subagent can run /build** — it has the workflow interpreter, orchestration-layer, ask-matt, web tools, and its own worktree. Not naked.
3. **Two agents can run workflows in the same repo** — in separate worktrees, no quarantine conflict.
4. **A manager agent can dispatch a workflow to a worker** — via subagent launch (subagent mode) or intercom workflow-request (separate-session mode).
5. **Hard decisions route to the manager agent** — via AGENT_DECISION_REQUIRED + intercom ask. No human in the loop for technical decisions.
6. **The bounded autonomous loop runs unattended** — the manager plans, dispatches, answers questions, detects done/stuck, merges, advances, ships. Self-advancing; never asks "should I do the next ticket?"
7. **Failure recovery works** — a worker crashes/sticks → the manager detects (status polling, 10-min idle) → relaunches (bounded 3 retries) → escalates if still failing. No human input.
8. **Self-healing intercom** — the broker dies mid-orchestration → the manager detects + restarts it → the flow continues.
9. **Autonomous merge + conflict resolution** — two workers conflict → the manager resolves by intent (resolving-merge-conflicts) → no human.
10. **Recursive delegation** — a worker can spawn read-only research/review subagents (depth-bounded at 2).
11. **The end-to-end dogfood completes autonomously with injected failures** — kill a worker + kill the broker → the manager recovers both → ships. Evidence: the commit + PR with no human turns after the single `/orchestrate`.
12. **The Temporal x MongoDB failure mode is fixed** — delegation works, children have web tools, no quarantine conflict, no output path collision. Regression tests prove it.
13. **Human-in-the-loop is still available** — for genuine human-owned decisions (money, legal, public-compatibility), USER_DECISION_REQUIRED still stops for a human. Autonomy is the default, not the only mode.
14. **95+ tests pass** (the v0.4 suite + the new v0.5 regression tests + the autonomous loop + failure recovery tests).

## Non-goals

- **Removing human-driven mode.** Coach + the 9-option menu + USER_DECISION_REQUIRED stay for humans who want them. v0.5 adds autonomous mode, doesn't replace manual.
- **Herdr integration.** We reverted the Herdr experiment. v0.5 is pure intercom + subagents + worktrees. No Herdr dependency.
- **Cross-machine coordination.** Intercom is same-machine only. v0.5 is same-machine multi-agent.
- **Broadcast messaging.** Intercom is 1:1. v0.5 uses 1:1 manager↔worker, not swarm broadcast. For 6+ agents, use parallel subagents (per AGENTS.md).

## Residual risks

1. **Subagent process coupling.** If the manager process crashes, workflow-worker subagents die. Mitigation: the workflow journal persists; the manager can resume on restart. Separate-session mode for long-running work.
2. **Worktree merge conflicts.** Two workers building in separate worktrees may conflict on merge. Mitigation: the manager resolves by intent (A4); only spec contradictions escalate.
3. **Agent decision quality.** The manager agent resolves technical decisions autonomously. If it's wrong, the workflow proceeds on a bad decision. Mitigation: the manager can still escalate to human for hard-to-reverse decisions (money/legal/public-compatibility).
4. **Intercom reliability.** We've seen the broker go stale, broken symlinks, wrong IDs. Mitigation: A3 (self-healing intercom) automates the fix we applied manually. The manager health-checks before each dispatch + answer.
5. **Stuck-worker false positives.** Status polling (D-6) might mark a worker stuck that's actually doing a long task. Mitigation: the 10-min idle threshold is configurable; the escalation ladder relaunches with fresh context (not a kill — the worker can finish if it recovers).
6. **Complexity.** Full multi-agent autonomy is architecturally complex. The risk is overbuilding. Mitigation: the 10 tickets are minimal; each solves one proven gap from the Temporal x MongoDB failure or one full-autonomy piece (A1–A6). The dogfood (ticket 9) proves the whole thing works with injected failures before shipping.
7. **The autonomy boundary.** "Fully autonomous" still has a boundary: money, legal, public-compatibility, release authority. The system is autonomous for ALL technical + product decisions. The human is only touched for the 4 hard-to-reverse classes. This is the honest definition of "fully autonomous" — not "no human ever," but "no human for technical work."
