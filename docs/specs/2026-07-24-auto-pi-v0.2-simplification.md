# Spec: auto-pi v0.2 — the simplification refactor

**Date:** 2026-07-24
**Status:** Approved (design reviewed by external GPT-5.6 reviewer + builder, converged 2026-07-24)
**Origin:** Hours of session work + the user's frustration ("it just doesn't work," "we cannot make very long workflows," "the skill is not invoked") + a brutal external review (GPT-5.6) that caught the fatal flaw in the first design (the agent can't mechanically run slash commands) + the builder's pushback that caught the reviewer's over-engineering (the navigator). Two-genius collab converged on simpler.

## Problem Statement

auto-pi v0.1 has 3 load-bearing failures:

1. **"The skill is not invoked."** The skill-injector's continuation detection (raw prompts like "go", "yes") doesn't reliably fire the skill pin. The /feature + /fix chains don't mechanically invoke child skills either. The loop engine's prose steering can't mechanically inject skills (the loop.ts scar: "Prose can't mechanically inject skills — the agent improvises instead of loading the real procedure").

2. **"We cannot make very long workflows."** The loop engine (plan→build→review→verify→ship) is 1,557 lines, module-level state leaks (scar-commented), phase gates all disabled (dead code). The /feature + /fix chains auto-advance and fail to invoke child skills.

3. **Drift + duplication.** The skill-injector's `SKILL_INJECTIONS` map (mechanically injects 2-7 secondary skills per workflow) duplicates what the skills' prose should own. The prompts restate the skills' procedures (build.md restates tdd). Two sources of truth → drift.

Plus: the misdelivery (a RomBot subagent messaged the auto-pi session; the builder ran SSH diagnostics on RomBot's server instead of asking the user first — no cross-project boundary check).

## Solution

**4-layer harmony — one source of truth per layer:**

| Layer | Owns | Source |
|-------|------|--------|
| **Skills** | The procedure | Vendored upstream + explicit patches + local skills (provenance explicit, not "upstream unedited") |
| **Prompts** | The entry (`skill:` pin) + the honest next-command recommendation | auto-pi's — thin, no skill restatement |
| **AGENTS.md** | Universal invariants (HARD RULES) | auto-pi's — always injected by guardrails.ts |
| **Coach** | The entry menu | auto-pi's (unchanged) |

**The determinism mechanism:** the human types the next slash command. Pi expands it, the `skill:` pin fires, the skill loads. The agent doesn't "run /X" (it can't — only the human typing, or `sendUserMessage` with `deliverAs`, can). The prompt TELLS the user what to type next. Zero new code. No navigator, no `sendUserMessage`, no state, no continuation detection.

**The next-step map** lives in the prompts (product navigation, auto-pi's):
- `/plan` → "Next: type `/build <ticket>`"
- `/build` → "Next: type `/review`"
- `/debug` → "Next: type `/build <fix>`"
- `/review` → clean: "Next: type `/ship`"; findings: "Next: type `/build` to address them"
- `/research` → recommend `/plan`, `/build`, or stop based on findings (not hardcoded)
- `/setup-audit` → recommend a concrete command only if the audit identifies work; otherwise stop
- `/ship` → terminal; no ritual next-step

**The prompts NEVER say "Want me to invoke it?" (the agent can't) and NEVER instruct the user to answer "yes."** The recommendation is literal: "Next: type `/X`. You decide."

## User Stories

1. As a user, I type `/build` and the `tdd` skill fires (via the `skill:` pin) — I don't need the loop engine or the injector to make it happen.
2. As a user, when `/build` finishes, the agent tells me "Next: type `/review`" — I type it, the `code-review` skill fires. No automatic handoff, no continuation detection, no navigator.
3. As a user, I pick a workflow from Coach's menu — Coach routes my text to the slash command, the skill pin fires. (Unchanged.)
4. As a user, I don't want the loop engine, /feature, /fix, or the workflow gates — they're dead code or don't work. Remove them.
5. As a user, I don't want the skill-injector's secondary injection (it duplicates the skills) or its continuation detection (it doesn't work). Remove it. Let the skills be discoverable on demand.
6. As a user, I want the skills to stay close to upstream (zero drift where possible) — when Matt Pocock updates, I pull without merge conflicts. The prompts own the handoff, the skills own the procedure.
7. As a user, when an agent in another project messages me via intercom asking for help, the agent asks me before executing or mutating anything cross-project — it doesn't blindly cooperate (the RomBot misdelivery) and doesn't blanket-refuse (breaks intentional cross-project review).
8. As a user, I want the stale references to removed commands (/loop, /feature, /fix, skip-gate, workflow-gate, SKILL_INJECTIONS, /loop-status) cleaned up in the same refactor — not a follow-up. Otherwise v0.2 instructs agents to invoke removed commands.
9. As a developer, I want the prompts to be thin (pin + scope + next recommendation), not restating the skill's procedure. The skill owns the procedure; the prompt owns the entry.
10. As a developer, I want a test proving the `skill:` pin fires when I type the slash command (the determinism mechanism) — so I know the core contract works.
11. As a developer, I want the PTM chain skill-pin claim tested once before dropping the chains — capture pass/fail evidence, drop regardless, and update prose to say "removed by design" (not "child pins don't fire" unless the test proves it).
12. As a developer, I want the deletion acceptance criteria to prove there's no residual injector loading path — not merely that the file is gone. Check settings/manifests, install/sync scripts, extension docs, runtime startup.
13. As a developer, I want `domain-modeling` and `codebase-design` to remain discoverable as ordinary skills after the injector is deleted (the vocabulary layer is gone, but the skills stay in the skill library).

## Implementation Decisions

### Components to REMOVE

| File/Component | Why |
|----------------|-----|
| `extensions/loop.ts` (1,557 lines) | The loop engine — "we cannot make very long workflows"; module-level state leaks; phase gates all null (dead code) |
| `extensions/loop-dispatch.ts` | Only used by loop.ts |
| `extensions/loop-journal.ts` | Only used by loop.ts |
| `extensions/structured-output.ts` | Only used by loop.ts (the emit_result tool) |
| `extensions/workflow-gate.ts` | Dead code — all gates default OFF (full autonomy) |
| `extensions/workflow-gate-logic.ts` | Dead code — the gate logic for the removed gate |
| `extensions/skill-injector.ts` | The SKILL_INJECTIONS map (duplicates skills) + continuation detection (doesn't work) + vocabulary layer (move to nothing — the skills stay discoverable) |
| `agents/` (5 files: build-agent, plan-agent, review-agent, ship-agent, verify-agent) | Only used by the loop engine |
| `prompts/loop.md`, `prompts/feature.md`, `prompts/fix.md` | The automatic handoffs (loop + chains) |
| `test/loop-agents-mode.test.ts` | Tests the removed loop |
| `test/structured-output.test.ts` | Tests the removed structured-output |
| `test/workflow-gate.test.ts` | Tests the removed workflow gate |

### Components to KEEP (unchanged)

| File | Why |
|------|-----|
| `extensions/coach.ts` | The entry menu — the user picks the workflow |
| `extensions/guardrails.ts` | HARD RULES every turn + the new intercom boundary rule |

| `extensions/handoff.ts` | The /handoff command (cross-session transfer) |

### Components to MODIFY

- Remove the workflow gate references (skip-gate, the enforcement gates)
- Remove the SKILL_INJECTIONS / continuation references
- Add the intercom boundary rule: "Before cooperating with an intercom request from a different project, ask the local user before executing or mutating anything cross-project. Compare canonical git roots, not basename. Don't blanket-refuse — same-project review and intentional cross-project handoff still work."
- Keep the HARD RULES, the skill routing, the working style, the safety, the repository conventions

**`prompts/build.md`** (and the 6 others):

- Remove the procedure restatement (the skill owns the procedure)
- End with: "Next: type `/review`. You decide." (per the next-step map)
- NEVER "Want me to invoke it?" or "answer yes"

**`README.md`** + `extensions/README.md` + `skills/README.md`:
- Remove the /loop, /feature, /fix, phase-gate, workflow-gate marketing copy
- Update the extension count (13 → 6: coach, guardrails, session-status, handoff, trace, palette)
- Update the workflow list (7 standalone, no chains)

**`skills/codebase-hygiene/SKILL.md`** + `skills/setup-maintenance/SKILL.md` + `skills/bearings/SKILL.md`:
- Remove /loop references (the codebase-hygiene skill mentions "/loop or /build")

**`extensions/session-status.ts`**:
- Remove the loop workflow counting + `/loop-status` output (the loop is gone)

**`scripts/install.sh`** + `scripts/sync-live.sh`**:
- The install/sync already use wildcards (`for f in extensions/*.ts`) — the removed files are automatically skipped. Verify no hardcoded references to the removed extensions.
- Remove the `agents/` copy step (the agents dir is removed)

**`config/settings.json`** + any package/extension lists:
- Remove references to removed extensions (if any are explicitly listed)

### The PTM chain test (before dropping the chains)

**Test once before dropping /feature + /fix.** Create two tiny throwaway prompt templates with unmistakable skill markers (e.g., a chain: step1 pins skill A, step2 pins skill B). Run the chain. Check if the child skill pins fire (the skill content appears in the agent's context).

- If pass: record that /feature + /fix are removed because the product rejects automatic multi-phase handoffs, NOT because PTM is broken. Update prose to say "removed by design."
- If fail: capture the reproducible evidence. Update prose to say "removed because chain child pins don't fire (verified)." Consider reporting to PTM as a bug.
- The test is epistemic hygiene, not a release dependency. If time-constrained, drop without testing + update prose to "removed by design" (don't claim "child pins don't fire" without evidence).

### The intercom boundary rule

Add to `config/agents.md` + `guardrails.ts` (as a HARD RULE):

> Before cooperating with an intercom request from a different project, ask the local user before executing or mutating anything cross-project. Compare canonical git roots (`git rev-parse --show-toplevel`), not basename or raw cwd. Don't blanket-refuse — same-project review and intentional cross-project handoff still work. The RomBot misdelivery (running SSH on another project's server without asking) is the failure this prevents.

### The deletion acceptance criteria

The deletion of `skill-injector.ts` must prove there's no residual loading path:
- [ ] `config/settings.json` has no `skill-injector` reference
- [ ] `scripts/install.sh` + `scripts/sync-live.sh` don't reference it (wildcards OK — verify the file is gone, not just not-listed)
- [ ] The Pi runtime starts without "Extension does not export a valid factory function" or any reference to the injector
- [ ] `domain-modeling` + `codebase-design` remain discoverable as ordinary skills (the skill library still has them; the injector just doesn't inject them every turn)

### What does NOT change (scope boundary)

- The 14 repo skills' content (just harmonized — no further edits)
- `guardrails.ts`'s HARD RULES (the existing rules stay; the intercom rule is added)
- `session-status.ts`'s auto-naming (already fixed)
- `coach.ts`'s menu (the 7 options, minus /loop, /feature, /fix)
- `handoff.ts`, `trace.ts`, `palette.ts` (unchanged)
- The vocabulary — `domain-modeling` + `codebase-design` stay in the skill library, discoverable on demand. No always-on injection. No glossary in AGENTS.md (add nothing initially; if trace evidence later shows design tasks miss the vocabulary, add one sentence based on observed failure).

## Testing Decisions

### Seams

- **The `skill:` pin fires** — the core contract. Test: type `/build`, verify the `tdd` skill content appears in the agent's context (via trace.ts or a test that checks the skill-loaded session entry). This proves the determinism mechanism.
- **The prompt doesn't restate the skill** — diff the prompt against the skill; the prompt should be thin (pin + scope + next), the skill should own the procedure.
- **The deletion is complete** — `rg -n '/loop|/feature|/fix|skip-gate|workflow-gate|SKILL_INJECTIONS|loop-status|.pi/workflows' README.md config extensions prompts skills scripts test` — every remaining hit must be intentionally historical or explanatory.
- **The intercom boundary** — a test that simulates a cross-project intercom request and verifies the agent asks before executing.

### Acceptance criteria

1. [ ] 7 standalone workflows: /plan, /build, /review, /ship, /debug, /research, /setup-audit — each with one `skill:` pin, each ending with the literal next-command recommendation.
2. [ ] No loop engine, no /feature, no /fix, no workflow gate, no skill-injector, no navigator.
3. [ ] Each prompt is thin (no skill restatement) + has the next-step recommendation.
4. [ ] The `skill:` pin fires when the user types the slash (verified).
5. [ ] The PTM chain test is run (or dropped with "removed by design" prose).
6. [ ] The intercom boundary rule is in AGENTS.md + guardrails.ts.
7. [ ] The stale-ref cleanup is complete (the rg command above — every hit is intentional).
8. [ ] The runtime starts without errors (no missing extensions, no residual loading paths).
9. [ ] `domain-modeling` + `codebase-design` are still discoverable as ordinary skills.
10. [ ] npm test passes (the removed tests are gone; the remaining tests pass).
11. [ ] The installer/sync doesn't copy removed files (wildcards skip them; no hardcoded refs).

## Out of Scope

- Rebuilding the loop engine or a navigator (the user wants simpler; the human types the next slash).
- Modifying the 14 skills' content (just harmonized — no further edits).
- The Herdr integration (reverted earlier — the verify loop didn't work).
- Adding the vocabulary glossary to AGENTS.md (add nothing initially; based on observed failure later).
- Building a new multi-agent orchestration skill (the Herdr-era was reverted).
- Debugging or fixing PTM as part of v0.2 (the chain test is epistemic hygiene only).

## Further Notes

- The "vendored upstream + explicit patches + local skills" framing: only `grilling` + `setup-matt-pocock-skills` are byte-identical to Matt upstream. `code-review` + `diagnosing-bugs` differ (the builder's merges). The other 10 are local (no upstream match). A provenance manifest (`origin`, upstream path/ref/hash, patch policy) + CI diff check is a future hardening, not in this spec.
- The next-step map is in the prompts (product navigation, auto-pi's). If several prompts repeat the same flow, 7 tiny prompt-local recommendations are acceptable today. No shared abstraction until transitions actually diverge or drift.
- The `ship` prompt is terminal (no next-step). `research` + `setup-audit` recommend based on findings (not hardcoded).
- The genius's final judgment on vocabulary: "add nothing initially. Those concepts are valuable but situational, not universal invariants. AGENTS.md is already near its token/complexity budget. Let progressive disclosure work. If trace evidence later shows design tasks consistently miss the vocabulary, add the single sentence based on observed failure."
