## The realization

auto-pi v0.3 built six workflow orchestrators (planning, build, review, ship, debug, research) that each independently route through the SDLC. **This duplicated routing that Matt Pocock's `ask-matt` skill already provides.**

`ask-matt` is a complete flow router over the engineering skills:

- **Main flow:** `grill-with-docs` → (prototype detour) → `to-spec` → `to-tickets` → `implement` (drives `tdd` internally + `code-review`) → commit
- **On-ramps:** `triage`, `diagnosing-bugs`, `wayfinder`
- **Standalone:** `grill-me`, `prototype`, `research`, `handoff`
- **Vocabulary:** `domain-modeling`, `codebase-design`
- **Upkeep:** `improve-codebase-architecture`

auto-pi's six orchestrators each re-derive a slice of this graph. The result: duplicated routing, conflicting instructions where orchestrator meets specialist (C-1: receiving-code-review IMPLEMENT vs review-workflow do-not-apply), a bloated contract modeling a parallel graph, and 81.3% of skill loads depending on the model choosing to read the right file.

**auto-pi's real value is not the routing. It is the autonomous orchestration layer:** state blocks, evidence gates, reread-after-phase protocol, compaction recovery, the separate ship phase, the review disposition flow, verification-before-completion, and the Security reviewer. Matt's skills have none of that.

v0.4 collapses the duplication. `ask-matt` becomes the routing brain. auto-pi becomes a thin orchestration layer wrapped around it. Coach stays the deterministic human-controlled entry.

## Target architecture

```
User types /plan
     │
     ▼
Coach (KEEPS the 9-option menu — deterministic entry, human-controlled)
     │
     ▼
Entry prompt loads:
   ask-matt (routing brain — the SDLC graph)
   + auto-pi orchestration layer (thin wrapper — state, evidence, compaction, human-controlled stops)
     │
     ▼
ask-matt routes:                   auto-pi layer adds:
"grill → spec → tickets"           - state block (phase + evidence)
                                   - evidence gates at each boundary
                                   - reread-after-phase protocol
                                   - compaction recovery (re-read ask-matt + layer)
                                   - HUMAN-CONTROLLED: stop at phase boundary
                                   - "Next: type /spec <ref>"
     │
     ▼
User types /spec → Coach → ask-matt (routing) + auto-pi layer (orchestration)
     │
     ▼
...human-controlled at every boundary
```

### Three layers, one chain of command

| Layer | Role | Owner |
| ------- | ------ | ------- |
| **Coach** | Deterministic 9-option menu. Human-controlled entry. Intercepts input, hands to the matching prompt. | auto-pi (`extensions/coach.ts`) — unchanged |
| **ask-matt** | The routing brain. Decides which specialist to read next based on where the work is in the SDLC. | Matt Pocock (external skill, pinned) |
| **Orchestration layer** | The autonomous driver mechanics: state blocks, evidence gates, reread protocol, compaction recovery, human-controlled stops, the unique auto-pi phases (ship, review disposition, verification, security). | auto-pi (NEW — one thin skill) |

## Open design decisions

### D-1: What does the orchestration layer skill look like?

**Proposal:** One skill, `orchestration-layer`, loaded by every Coach entry prompt alongside `ask-matt`. It defines:

- The state block schema (phase, evidence, artifacts)
- The evidence gates (per-phase requirements)
- The reread-after-phase protocol
- The compaction recovery protocol (re-read ask-matt + this layer)
- The human-controlled stop rule ("emit state, tell user 'Next: type /X', stop")
- The unique auto-pi phases (ship, review disposition, verification, security) as layer-level phase definitions

**Alternative:** Per-Coach-option layer prompts (plan-layer, build-layer, etc.) each adding option-specific state. Rejected — reintroduces the 6-orchestrator duplication.

**Decision needed:** Confirm the single-skill approach.

### D-2: How does ask-matt get loaded?

**Proposal:** Each Coach entry prompt's `skill:` frontmatter pins both `ask-matt` and `orchestration-layer`. Pi's prompt-template-model supports multiple `skill:` pins (verify this). If not, the prompt pins `orchestration-layer` and the layer's first instruction is "read ask-matt at <absolute path> completely".

**Decision needed:** Confirm multi-pin is supported; if not, confirm the read-on-entry fallback.

### D-3: Fork ask-matt or depend on it?

**Proposal:** **Depend on it, pin the version.** ask-matt is installed from Matt's repo. We add provenance (commit hash + SHA-256) like we did for code-review/diagnosing-bugs. `check-drift.sh` catches upstream changes. We do NOT fork ask-matt — we want upstream improvements to flow in. If Matt changes ask-matt in a way that breaks the layer, the drift check flags it for manual review.

**Rationale:** ask-matt is a routing reference, not a procedure we need to modify. Forking would freeze us at a version and lose upstream improvements. The orchestration layer is where auto-pi's customizations live.

**Alternative:** Fork ask-matt into the repo. Rejected — we'd maintain a routing graph we explicitly want Matt to own.

**Decision needed:** Confirm depend-with-provenance.

### D-4: Security review methodology — brief inside the layer or a dedicated specialist?

**Proposal:** **A dedicated `security-review` specialist skill** in the repo, read by the layer during review. It has a smell catalog (injection, authn/authz, secrets, unsafe deserialization, SSRF, path traversal, unsafe operations) comparable to code-review's Fowler baseline. This is better than a 4-word parenthetical inside the layer.

**Alternative:** A Security brief section inside the layer. Rejected — it would bloat the layer and conflate routing with procedure.

**Decision needed:** Confirm the dedicated specialist approach.

### D-5: What happens to the 3 orphans?

**Proposal:**

- `decision-hold-lifecycle` → wired into the layer's planning phase (persist unresolved design decisions) and review phase (persist unresolved review decisions).
- `memory-compounding` → wired into the layer's ship-complete phase (post-work memory hygiene, runs after the work is done).
- `session-handoff` → documented as a standalone utility invoked via `/handoff` (the ext cmd). The layer's compaction-recovery mentions it as the escape hatch when context is too degraded to recover in-place.

**Decision needed:** Confirm the wirings (especially session-handoff — is standalone-enough, or should it be a Coach option?).

### D-6: What happens to the contract + 117 tests?

**Proposal:** The contract is rewritten to model **ask-matt's graph + the orchestration layer's phases**, not the 6 parallel workflows. The tests are rewritten to validate:

- ask-matt is pinned + has provenance + passes drift check
- The orchestration layer skill exists + has the required structural sections (state, evidence, reread, compaction, human-controlled stop)
- The layer's phases (ship, review disposition, verification, security) are well-formed
- The 14 specialists ask-matt routes to all exist at runtime paths
- The 3 orphans are wired or documented
- The audit defects (C-1, G-1, D-1, D-2, O-1, O-2, O-3) are resolved (regression tests)

The 6-workflow-specific tests are removed (they test a graph we no longer maintain). The drift-checker behavioral tests stay (they're genuinely valuable).

**Decision needed:** Confirm the contract + test rewrite scope.

## Acceptance criteria

The refactor is complete when:

1. **ask-matt is the routing brain** — pinned by every Coach entry prompt, with provenance + drift automation.
2. **One orchestration-layer skill** wraps ask-matt — state, evidence, reread, compaction, human-controlled stops.
3. **The 6 workflow orchestrators are gone** — no `skills/*-workflow/` directories, no references in prompts/AGENTS.md/Coach.
4. **Coach keeps the 9-option menu** — unchanged entry UX.
5. **The unique auto-pi phases live in the layer** — ship, review disposition, verification, security.
6. **The 3 orphans are wired or documented** — no dead skills.
7. **The audit defects are resolved** — C-1, G-1, C-2, D-1, D-2, O-1, O-2, O-3, Pattern 1 (regression tests prove it).
8. **The contract + tests model v0.4** — ask-matt's graph + the layer, not 6 parallel workflows.
9. **Human-controlled progression is preserved** — the layer stops at phase boundaries, tells the user "Next: type /X", does not auto-advance.
10. **`npm test` passes** — the new suite is green.
11. **Live synchronization + `/reload`** — the running Pi session uses v0.4.

## Non-goals

- **Mechanical specialist-read enforcement.** The specialist reads stay probabilistic (model must call `read`). v0.4 makes the routing brain deterministic (pinned ask-matt) but does not change how specialists are loaded. A mechanical enforcement layer is a future concern.
- **Compaction recovery mechanical safety net.** The layer improves compaction recovery (re-read one skill + ask-matt, not 6) but the re-read is still a model instruction. A mechanical safety net is a future concern.
- **Context bloat / catalog pruning.** 119 skill descriptions in the system prompt is acknowledged but out of scope.
- **Removing the Coach menu.** You chose to keep it. Not in scope.
- **Autonomous auto-advance.** You chose human-controlled. The layer stops at boundaries.

---

## Residual risks (acknowledged, not resolved)

1. **ask-matt is an external dependency.** If Matt changes ask-matt's routing in a breaking way, the layer breaks. Mitigated by provenance + drift check, but not eliminated.
2. **Compaction recovery is probabilistic.** The layer is one skill to re-read (better than 6), but the model must still choose to re-read it after compaction.
3. **Specialist reads are probabilistic.** 81.3% of loads stay model-dependent. The routing brain is deterministic; the procedures are not.
4. **The layer could bloat.** If the unique auto-pi phases (ship, review, verification, security) grow, the layer becomes a mega-skill. Mitigated by extracting security to a dedicated specialist (D-4) and keeping the layer thin.
5. **Test coverage stays mostly static.** The rewritten tests still validate documentation consistency, not runtime behavior. The 6 behavioral drift-checker tests stay valuable; the rest stay static. This is an inherent limitation of prompt-based orchestration testing.
