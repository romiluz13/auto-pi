## The realization

auto-pi v0.3 built six workflow orchestrators (planning, build, review, ship, debug, research) that each independently routed through the SDLC. **This duplicated routing that Matt Pocock's `ask-matt` skill already provides.**

`ask-matt` is a complete flow router over the engineering skills:

- **Main flow:** grill → (prototype detour) → to-spec → to-tickets → implement (drives tdd + code-review) → commit
- **On-ramps:** triage, diagnosing-bugs, wayfinder
- **Standalone:** grill-me, prototype, research, handoff
- **Vocabulary:** domain-modeling, codebase-design
- **Upkeep:** improve-codebase-architecture

auto-pi's six orchestrators each re-derived a slice of this graph. The result: duplicated routing, conflicting instructions where orchestrator met specialist, a bloated contract modeling a parallel graph, and 81.3% of skill loads depending on the model choosing to read the right file.

**auto-pi's real value is not the routing. It is the orchestration layer:** state blocks, evidence gates, reread-after-phase, compaction recovery, the separate ship phase, the review disposition flow, verification-before-completion, and the Security reviewer. Matt's skills have none of that.

v0.4 collapses the duplication. `ask-matt` becomes the routing brain. auto-pi becomes a thin orchestration layer wrapped around it. Coach stays the deterministic human-controlled entry.

## The v0.4 architecture: three layers

```
User types /plan
     │
     ▼
Coach (deterministic 9-option menu — human-controlled entry)
     │
     ▼
Entry prompt pins: orchestration-layer
     │
     ▼
orchestration-layer reads ask-matt (routing brain) + adds mechanics:
  - state block (phase + evidence + artifacts)
  - evidence gates at each boundary
  - reread-after-phase protocol
  - compaction recovery
  - human-controlled stop ("Next: type /X")
     │
     ▼
ask-matt routes to the specialist for the current SDLC phase
     │
     ▼
specialist SKILL.md (brainstorming, tdd, code-review, etc.)
     │
     ▼
reread orchestration-layer + ask-matt → next phase
```

| Layer | Role | Owner |
| ------- | ------ | ------- |
| **Coach** | Deterministic 9-option menu. Human-controlled entry. Intercepts input, hands to the matching prompt. | auto-pi (`extensions/coach.ts`) — unchanged |
| **ask-matt** | The routing brain. Decides which specialist to read next based on where the work is in the SDLC. Pinned external skill with provenance + drift automation. | Matt Pocock (external, pinned) |
| **orchestration-layer** | The mechanics. State blocks, evidence gates, reread-after-phase, compaction recovery, human-controlled stops, and the unique auto-pi phases (ship, review disposition, verification, security). | auto-pi (one thin skill) |

## Audit defects resolved

All 9 defects from the 5 parallel reviewer audits are resolved in v0.4:

| Defect | Severity | Resolution |
| -------- | ---------- | ----------- |
| **C-1** receiving-code-review IMPLEMENT vs review do-not-apply | HIGH | The layer's review-disposition phase explicitly overrides receiving-code-review's IMPLEMENT step (skip step 6 → disposition recording; fixes happen in /build). One place, not a conflict. |
| **G-1** Phase 6 cleanup gap (debug instrumentation left in code) | MEDIUM | The layer's diagnose phase carries Phase 6 cleanup into post-fix (remove [DEBUG-...] tags, delete throwaway prototypes, verify repro no longer reproduces). |
| **C-2** diagnosing-bugs Phase 5 conflict | MEDIUM | The layer's diagnose path: "Follow Phases 1–4. Skip Phase 5 (fix happens in tdd). Execute Phase 6 (cleanup) after the fix in tdd." |
| **D-1** Diagnose phase duplicated in build + debug | MEDIUM | ask-matt routes to diagnosing-bugs once. The layer adds the diagnose phase once. No duplication. |
| **D-2** build-workflow inlines verification | MEDIUM | The layer reads verification-before-completion in build-complete AND ship. One source of truth. |
| **O-1/G-5** Security review has no methodology | MEDIUM | `security-review` specialist created (8-category smell catalog + review brief + severity guidance). |
| **O-2** Disposition categories only in orchestrator | MEDIUM | The layer owns the 4 disposition categories. receiving-code-review is the driven procedure. |
| **O-3** Severity mapping undefined | MEDIUM | The layer defines the axis→severity transformation (Standards/Spec/Security → CRITICAL/HIGH/LOW). |
| **Pattern 1** 3 specialists tell agent to "run" slash commands | LOW | Fixed: "run /X" → "tell the user to run /X" in code-review, diagnosing-bugs, codebase-hygiene. |
| **The 3 orphans** (decision-hold, memory-compounding, session-handoff) | MEDIUM | Wired into the layer or documented as standalone. |

### Defects NOT resolved by v0.4 (acknowledged residual risk)

| Defect | Why it remains |
| -------- | --------------- |
| Compaction recovery is probabilistic | The layer makes it better (re-read one orchestration skill + ask-matt, not 6 orchestrators), but the re-read is still a model instruction. No mechanical safety net. |
| 81.3% probabilistic load rate | The routing brain (ask-matt) is read on entry (stronger than v0.3's probabilistic specialist reads). The specialist reads stay probabilistic (model must call `read`). This is the inherent limitation of prompt-based orchestration. |
| Context bloat (119 skill descriptions) | Out of scope for v0.4. Tracked as a future concern (catalog pruning). |

## Residual risks (acknowledged, not resolved)

1. **ask-matt is an external dependency.** If Matt changes ask-matt's routing in a breaking way, the layer breaks. Mitigated by provenance + drift check (`config/pinned-deps.json` + `scripts/check-drift.sh`), but not eliminated.
2. **Compaction recovery is probabilistic.** The layer is one skill to re-read (better than 6), but the model must still choose to re-read it after compaction.
3. **Specialist reads are probabilistic.** The routing brain is read on entry; the specialist reads stay model-dependent. This is the inherent limitation of prompt-based orchestration.
4. **The layer could bloat.** If the unique auto-pi phases grow, the layer becomes a mega-skill. Mitigated by extracting security to a dedicated specialist (`security-review`) and keeping the layer thin.
5. **Test coverage stays mostly static.** The rewritten tests (91/91 pass) still validate documentation consistency, not runtime behavior. The 6 behavioral drift-checker tests stay valuable; the rest stay static. This is an inherent limitation of prompt-based orchestration testing.
